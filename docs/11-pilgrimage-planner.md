# 11 · 巡礼规划：确定性算法 + LLM

## 本章目标

读完能回答：

- 用户说"我周六上午从新宿出发，有 4 个小时，想去《孤独摇滚》圣地"，系统内部发生了什么？
- 为什么挑点和排路线不交给 LLM，而是写成算法工具？LLM 在这里负责什么？
- 怎么把几十个散落的地点分成"步行能串起来的一片"？
- 时间预算内挑哪几个点、按什么顺序走——这是什么问题，用了什么启发式？
- 日本有没有免费的电车换乘 API？用的时候要注意什么？
- 怎么让 LLM 不把工具结果说错（比如把"不含返程"说成"含往返"）？

## 核心概念

### 起因：让 LLM 自己挑点，效果不好

接入真实数据后（[03 章](03-mcp-server.md#真实数据anitabi-快照)），一部作品动辄几十处圣地。最初的做法是让 LLM 用 `list_spots` 拿到全部地点，自己挑、自己调 `plan_route` 排顺序。实测问题：

- **不稳定**：同一个问题，这次挑 8 个，下次挑 10 个，标准不一
- **贵**：几十个地点的数据全进上下文，一轮 1~3 万 token（[03 章实测](03-mcp-server.md#工具接口为什么要改)）
- **它不擅长这个**：在时间预算里挑点是组合优化，算步行时间是算术——都是 LLM 的弱项

### 别人怎么做：参考了 5 个开源项目

在 GitHub 上找了几个同类项目读 README 和设计文档，结论惊人地一致：

| 项目 | 借鉴的点 |
|---|---|
| [anime-pilgrimage-agent](https://github.com/jsssjsgnk/anime-pilgrimage-agent) | "**距离、时间、价格的计算由确定性代码负责，不交给模型**"；分 Route A（全部候选）和 Route B（约束下可执行的子集），**列出被省掉的点和原因** |
| [MiriaGo 路线规划 Skill](https://github.com/BilyHurington/miriago-route-planner-skill)（MIT） | 用最小生成树 + 尺寸上限切"步行大小的片区"；片区内最近邻 + 2-opt 排序；所有估算值明确标注；**不排电车时刻** |
| [anime-pilgrimage-skills](https://github.com/GrayEnergy/anime-pilgrimage-skills) | 按用户可用时间生成 Route B；没有地图 API key 时生成 Google Maps 路线链接兜底 |
| [junrei_navi](https://github.com/realMisakaMikoto/junrei_navi) | 唯一真正算公交的，用 Google（付费额度，作者自己说不保证长期可用） |
| [emoroute-tokyo](https://github.com/Jamy0ung/emoroute-tokyo) | 目标函数写得清楚：先在预算内最大化点数，再比其他指标；避免"只挑很少几个点拉高平均分" |

于是分工定为：

```
LLM：  理解需求（作品、出发地、时间、日期）→ 调一次 plan_pilgrimage → 写导语、看点、注意事项
代码： 选片区 → 查步行时间矩阵 → 查电车换乘 → 在预算内挑点排序 → 输出结构化行程
前端： 把结构化行程渲染成图文攻略卡片 + 地图路线
```

### 定向越野问题

"每个点有价值、走路和停留都花时间、总时间有上限，怎么挑点和排顺序让价值最大"——这是运筹学里的**定向越野问题**（Orienteering Problem）。它是 NP 难的（比旅行商问题还多了"挑哪些点"这一层），精确求解不现实。demo 规模（每次 ≤20 个候选点）用启发式足够：

1. **贪心插入**：每一轮试遍"哪个点 × 插在路线哪个位置"，选「价值 ÷ 新增时间」最高、且不超预算的那个
2. **2-opt**：把路线中间一段反过来，总时间变短就保留，直到改不动

分层和项目其他地方一样：**算法是纯函数（`planner.py`），网络客户端由参数注入（`itinerary.py`）**。算法可以用固定输入做确定性测试——同样的输入一定得到同样的路线，这也是将来做评测的基础。

### 片区：最小生成树 + 直径上限

[anitabi.py 的 build_areas()](../backend/mcp_servers/seichi/anitabi.py) 在生成快照时离线算好，每部作品分成若干"步行能串起来的一片"：

1. 在所有地点上建**最小生成树**（MST）：用总长最短的边把所有点连起来（Prim 算法，O(n²)，一部作品最多几百个点，离线算一次够快）
2. 剪掉长于 **1.4 km** 的边 → 树断成几块
3. 某块直径超过 **2.6 km** 或超过 **25 处**，就剪掉它内部最长的一条边，递归切分

参数取自 MiriaGo 的 balanced 档。MiriaGo 还会按局部密度找断点，这里没做。

**为什么不用固定半径连片？** 上一版实验用"1.5 km 以内连成一片"，《上低音号》宇治的 33 处连成了一个 **7.7 km 的长条**——地点一个挨一个，链式地连了下去。固定半径只管相邻两点，管不住整体大小；MST 加直径上限能把长条切成几段。实测结果：

| 作品 | 地点 → 片区 | 前几个片区 |
|---|---|---|
| 孤独摇滚！ | 41 → 14 | 下北泽（12 处，直径 1.0 km）/ 金泽八景（8 处）/ 江之岛（8 处）/ 御茶之水 |
| 吹响吧！上低音号 | 40 → 11 | 北宇治高校一带（6 处 268 镜头，1.3 km）/ 宇治桥一带（16 处，1.2 km）/ 六地藏 |
| 你的名字 | 61 → 21 | 四谷（16 处，2.4 km）/ 新宿 / 飞驒古川 |

全部 1559 部作品共 10599 个片区，其中 6845 个只有一处（郊外孤立的点）。

快照 v2 还加了两样东西：

- **社区备注**（`notes`）：原始数据的 `mark` 字段，38% 的地标有。内容很实用——"此处拍摄需事先征得许可，下午 5 点后禁止拍照""停车场已撤除，无法进入""营业 11~14 点，周一二休息"。同一地点的备注去重，最多 3 条、每条 200 字
- **原始数据缓存**：下载的原始文件存在 `data/anitabi_raw/`（不进 git）。调算法后 `--offline` 重建，不必再请求 Anitabi

### 选片区与候选

[planner.py](../backend/mcp_servers/seichi/planner.py)：

```python
def rank_areas(areas, locations, start, budget_min): ...
```

- 片区价值 = 最热门的 10 个地点的价值之和（去不完的点不该加分）
- 给了出发地：按直线距离粗估路上时间（等车 15 分钟 + 35 km/h），价值按「剩余时间比例」打折；单程超过预算一半的排到最后

候选点 = 主片区 + 中心离得不远（2.5 km 内）的相邻片区，按价值取前 20 个。相邻片区也纳入，是因为切分是按直径硬切的，宇治桥和北宇治高校虽然分在两片，时间够的话完全可以一起走。

**价值用对数**：`spot_value = 1 + log2(镜头数)`。北宇治高校一处 214 个镜头，按镜头数算它一个抵得上其他二十个，算法会为了它牺牲所有其他点。对数让价值随镜头数增长但递减。

### 预算内挑点排序

```python
def plan_route(values, dwell, minutes, budget_min, origin=None) -> RoutePlan:
```

- `minutes`：步行时间矩阵（分钟），来自 OSRM 的 table 接口——一次请求拿到 n×n 全部结果
- `dwell`：每处停留时间，按镜头数 10 / 15 / 20 分钟（镜头越多，值得拍的角度越多）
- `origin`：有出发地时固定为第一站

**一个实测前的设计错误**：最初没有出发地时，拿"价值最高的点"当第一站开始贪心。写测试时构造了一个反例——价值最高的点很偏（离谁都要走 50 分钟），算法拿它开头后就只能去它一个，而另外两个挨在一起的点加起来价值更高。改成**每个点都试一次当第一站，取总价值最高的方案**；候选最多 20 个，跑 20 次贪心也只要几毫秒。这个反例留在了 [test_planner.py](../backend/tests/test_planner.py) 里。

没去成的点附原因：离路线上所有点都超过 30 分钟步行的是"太远"，其余是"时间预算不够"。

### 电车：Transit API

[transit.py](../backend/mcp_servers/route/transit.py)。调研了几种免费方案：

| 方案 | 能查什么 | 门槛 | 结论 |
|---|---|---|---|
| **Transit API**（`api.transit.ls8h.com`，个人维护） | 换乘路线 + 时刻 | 免费、不要 key | ✅ 采用 |
| ODPT 公共交通开放数据中心（官方） | 时刻表等原始数据 | 免费注册 | 不提供路线搜索，要自己搭 OpenTripPlanner |
| 駅すぱあと API | 换乘搜索 | 免费方案需申请 | 免费额度是否含路线搜索未确认 |
| Google Directions（公交） | 换乘搜索 | 绑卡付费 | 不用 |

Transit API 实测（2026-10-21）：新宿→下北沢 20 分钟、东京→金泽八景 69 分钟、藤泽→片濑江之岛 15 分钟、京都→宇治 48 分钟，都给出了合理的换乘。覆盖 1106 个数据源（JR 各线、东京 Metro、都营、小田急、京急、江之电、京阪……），但**没有票价**，响应 2~30 秒不等。

它是个人服务、没有可用性承诺，条款要求不大量请求、标注非官方。所以客户端：

- 同样的查询只发一次（内存缓存），两次请求至少间隔 1 秒
- **超时、出错一律返回 None**，由调用方退回直线距离粗估并标注 `estimated`——它挂了不能让整个规划失败
- 结果带 `source`，攻略卡片显示「非官方，以运营商官方信息为准」
- **永远附上 Google Maps 公交导航链接**（URL 方案，不需要 API key）：粗估时用户点开就能看真实换乘

到达时刻用换乘结果里的 `arrive`，不用"出发时间 + 时长"：实测 10:00 出发、车程 24 分钟，但 10:04 才有车，10:27 到——相加会算成 10:24。

### 编排与输出

[itinerary.py 的 make_itinerary()](../backend/mcp_servers/seichi/itinerary.py) 串起整个流程：

```
选片区 → 候选点 → 出发地离最近的候选点 ≤1.5 km？
                    ├─ 是：出发地作为步行起点
                    └─ 否：查电车到最近的候选点，它固定为第一站
         → OSRM 步行矩阵 → plan_route() → 逐站算到达时刻 → 组装
```

输出（约 6000 字符）既给 LLM 写回答，也给前端画卡片：

```json
{"anime_title": "孤独摇滚！", "area": {"id": "328609-1", "name": "下北沢SHELTER"},
 "budget_min": 240, "total_min": 225, "walk_km": 3.4, "walk_source": "OSRM 按实际路网计算",
 "access": {"depart": "10:04", "arrive": "10:27", "duration_min": 24, "rides": […], "estimated": false, …},
 "stops": [{"order": 1, "name_ja": "ADRIFT", "episodes": [4], "image": "…", "notes": […],
            "dwell_min": 10, "walk_from_prev_min": 0, "arrive_at": "10:27"}, …],
 "omitted": [{"name": "…", "reason": "时间预算不够"}],
 "other_areas": [{"area_id": "328609-2", "name": "金沢八景マンション前", "spots": 8, …}],
 "walking_route_url": "https://www.google.com/maps/dir/?api=1&…",
 "assumptions": ["每处停留 10~20 分钟…", "总时长含去程交通，不含返程"]}
```

### 让 LLM 说对：边界要写在数据里

第一次浏览器实测，LLM 的回答里有两句错话：

- "总时长约 225 分钟，**含往返电车**，14:00 前后就能回到新宿"——实际只算了去程
- "步行距离与时间为**路线服务估算值**"——实际是 OSRM 按真实路网算的

两处都不是 LLM"笨"，而是**工具输出没写清楚边界，它就按常识补全了**。修法不是改 prompt 叮嘱，而是把事实写进数据：`assumptions` 加上「总时长含去程交通，不含返程」，加 `walk_source` 字段。第二次实测，它就主动说"不含返程，回京都站要另留约 30 分钟"。

### 攻略卡片

[GuideCard.tsx](../frontend/src/components/GuideCard.tsx)：`plan_pilgrimage` 成功后，在工具步骤下面渲染图文攻略——换乘（线路、方向、上下车站、时刻）、每站的动画截图、到达时间、停留、集数、镜头数、社区备注，站与站之间的步行分钟，Google Maps 步行路线链接，没安排的点（可展开）和其他片区。

**图片、时间、链接全部来自工具数据，不让 LLM 抄写**——和地图不解析 LLM 文字（[10 章](10-frontend.md#地图只认结构化数据)）是同一个原则。所以 system prompt 告诉 LLM：卡片上已经有的不要再罗列，只写导语、3~5 个重点站的看点、注意事项（从 notes 里挑）、估算说明。

解析逻辑在纯函数 [guide.ts 的 parseGuide()](../frontend/src/chat/guide.ts)，卡片和地图都用它（地图把站点画成编号路线、出发地画成地点标记）。

## 设计取舍

| 决策 | 备选 | 为什么这样选 |
|---|---|---|
| 一个组合工具 `plan_pilgrimage` | LLM 用 list_spots + plan_route 自己拼 | 挑点是组合优化、算时间是算术，交给代码稳定可复现；参考的开源项目全部这样分工 |
| 片区离线算好存进快照 | 每次请求时现算 | 1559 部作品连同合并、分区 `--offline` 重建实测 2 秒，请求时零开销 |
| MST + 直径上限 | 固定半径连片；k-means | 固定半径实测连出 7.7 km 长条；k-means 要预先定片区个数，作品之间差异太大 |
| 贪心插入 + 2-opt | 精确求解（整数规划） | NP 难；≤20 个候选时启发式几毫秒出结果，质量够用 |
| 价值用 log(镜头数) | 直接用镜头数；用 priority | 镜头数线性会让一个超级热门点压倒一切；priority 含义没有文档 |
| Transit API + 粗估兜底 + Google Maps 链接 | 不做电车；只给链接 | 免费、实测准确；个人服务不稳定，所以三层兜底，任何一层挂了规划照常 |
| 只算去程，不算返程 | 返程也查 | 用户结束的地点不确定（可能接着去别处），返程查了也常常没用；但要在输出里写明 |
| 卡片数据来自工具，LLM 只写评论 | LLM 输出 Markdown 图文攻略 | LLM 抄 URL 和数字会错；而且卡片能交互（链接、展开） |
| 边界写进数据（assumptions、walk_source） | prompt 里叮嘱"不要说含往返" | prompt 防不胜防；事实放在数据里，LLM 照着说就不会错 |

## 延伸思考

1. 现在每处停留按镜头数给 10 / 15 / 20 分钟。有的地点是"路过拍一张"，有的是要进去吃饭的店（社区备注里常有营业时间）。停留时间能从数据里推断得更准吗？
2. 规划只选一个主片区（加相邻片区）。用户有一整天时，"上午下北泽、下午江之岛"这种跨片区行程该怎么规划？片区之间的电车时间要查几次？
3. `rank_areas` 用直线距离粗估去每个片区的时间来排序，只对选中的那一个查真实换乘。如果粗估的排序和真实的不一样（比如直线近但要换乘三次），会怎样？值得为前三名都查一次吗？
4. 现在整套规划是确定性的：同样的输入一定得到同样的输出（除了换乘接口）。这对"评测"意味着什么？怎么设计一组测试用例，衡量"规划得好不好"（而不只是"有没有报错"）？
5. LLM 说错"含往返"那件事，换个模型还会发生吗？"把边界写进数据"和"在 prompt 里叮嘱"，哪个对换模型更稳？
